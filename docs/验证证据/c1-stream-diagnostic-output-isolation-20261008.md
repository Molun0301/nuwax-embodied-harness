# StreamBus 诊断输出解耦（2026-10-08）

基线：`ba20fb108ab910cc20469b6e0116f4e9bc68efbd`。

## 可复现阻塞

同步订阅回调结束后，超过既有5ms条件的性能警告仍直接调用文件/控制台日志处理器。调用方虽然没有持有总线数据锁，却仍拥有全局分发责任；慢日志处理器会让当前发布者和另一个无关同步发布者一起等待。内部日志过滤只避免递归写入日志流，并不隔离文件/终端I/O。

使用真实StreamBus、受控性能计数器和门控日志处理器复现：旧代码中两个发布者均须等处理器释放；候选中两者都能在处理器仍被阻塞时完成。该检查证明因果顺序，不是生产时延或发生频率测量。

## 实现范围

- 每个StreamBus有一个私有、首次需要时才启动的诊断输出线程。仅移动四个既有诊断输出入口，不改变同步回调、游标、重入、异步订阅顺序，也不占用原异步订阅消费线程
- 既有LogRateLimiter在事件发生时决定限流，保留suppressed_count和原时间窗口。原logger、消息、关联字段、异常文本及文件/终端可见性保持，内部递归过滤继续生效
- 交接内容序列化为独立字节，不保留异常对象、traceback/frame或原始流payload引用。默认最多64条、256KiB已接收日志，包含在途写入；短条件锁仅用于队列交接，不在锁内执行处理器
- 满载、超大、关闭后提交、准备失败及输出失败都有明确计数；缺口合并后由输出线程报告。单次循环同时领取一个缺口和一条已接收记录，避免持续拒绝使已接收记录饥饿；缺口报告自身失败不递归记录
- `status().diagnostic_log`暴露容量、在途数量/字节、缺口、输出失败和线程状态；固定缺口摘要不计入已接收payload字节预算
- shutdown撤销原本未领取的回调后，使用同一截止时间等待在途同步/异步生产者和诊断输出。超时返回False，依赖保留供后续关闭；Runtime关闭流程尊重这个结果，不提前移除日志流处理器

没有改变原5ms触发条件和订阅业务校验，没有新增内容哈希、日志持久化数据库或通用任务执行框架。

- 既有EventBus32、地图修订31、运行时事件日志24、感知scene分发9、感知分发11，共107项通过
- 另直接运行既有6项取消及6项PreparedChecks通过；其中6项PreparedChecks与地图集合重复，不累加为额外独立覆盖
- 原取消检查启动器在导入缺失LCM时受阻，未标通过；直接runner执行相同测试方法且禁止socket/子进程/grpc，不以LCM桩替代真实设备链路
- 因果比较首次未在构造前替换logger，导致候选门闩未挂接；修正测试夹具顺序后通过，原失败日志保留。产品代码未因此修改
- 独立审查没有发现受支持路径的生命周期/顺序回归；全部新增定向测试亦通过

## 边界

本阶段隔离的是日志处理器、轮转文件及控制台输出。消息格式化、JSON准备和异常格式化仍在发布线程；traceback格式化可能经linecache读取源文件，不能声称全部诊断文件系统I/O已异步化。队列预算不包括短暂格式化/序列化分配或固定缺口报告。并未测CPU、吞吐、RSS、Go2实机或精确Python3.8.10。

日志处理器故障或容量耗尽不保证无损，必须读取缺口/失败计数；没有把日志投递成功等同于业务动作成功。通用EventBus的全局同步顺序契约未改变，不能将本阶段说成全平台回调已完全解耦。
