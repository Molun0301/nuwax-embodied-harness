# 轻量安装与自动发布

Nuwax Embodied Harness（NEH，具身运行框架）通过设备管理页安装、更新和运行。设备先安装独立管理程序，再按所选模块下载业务包及其依赖。网页与 CLI（命令行界面）使用同一套计划、任务记录、配置和版本目录。

首发配置版本为 `0.1.0`。实际可安装版本以[仓库发布页](https://github.com/Molun0301/nuwax-embodied-harness/releases)和管理页刷新取得的版本目录为准；下表是自动发布配置声明的范围，发布流程要求全部目标成功后才公开版本。仓库保持私有，下载需要仓库访问权限。

## 首发平台和模块

| 发布目标 | 系统与解释器 | 构建环境 |
| --- | --- | --- |
| `ubuntu24-x86_64` | Ubuntu 24.04、x86_64、Python（编程语言）3.12 | GitHub Actions（持续集成服务）的 Ubuntu 24.04 x86_64 执行器 |
| `ubuntu24-aarch64` | Ubuntu 24.04、ARM64（64位精简指令集架构）、Python 3.12 | Ubuntu 24.04 ARM64 执行器 |
| `go2-jetson` | Go2、Ubuntu 20.04、ARM64、Python 3.8 | 真正 ARM64 执行器内的固定 Ubuntu 20.04 容器 |

三个目标各提供下列七种组合，共21个业务包：

| 预设 | 包含模块 | 用途 |
| --- | --- | --- |
| `core` | 基础网关 | 控制台、标准数据接入和接口 |
| `geometry` | 基础网关、几何建图 | 使用已提供的里程计与传感器输入 |
| `navigation` | 基础网关、几何建图、导航 | 导航与探索；定位输入由设备配置提供 |
| `fastlio2` | 基础网关、几何建图、FastLIO2 | 激光惯性定位与建图 |
| `pointlio` | 基础网关、几何建图、PointLIO | 另一种激光惯性定位与建图前端 |
| `fastlio2-navigation` | FastLIO2组合及导航 | 基于 FastLIO2 的三维导航与探索 |
| `pointlio-navigation` | PointLIO组合及导航 | 基于 PointLIO 的三维导航与探索 |

FastLIO2与PointLIO每次选择一种。安装器自动补齐基础依赖，并按系统、架构、Python版本、机器人类型和完整模块集合查找业务包。网页列出模块用途不代表任意组合都有已发布业务包；计划中没有匹配包时会显示缺项，不会把其它组合替换进来。

以下能力尚未进入本次默认发布目录：

| 范围 | 仍缺少的发布输入或验证 |
| --- | --- |
| `perception` 本地视觉感知 | CLIP（图文对齐模型）固定源码的发行轮子记录仍未完成；缺少目标平台固定的 `torch`、`torchvision` 约束及视觉模型的逐文件下载地址、修订、摘要和大小 |
| `memory` 本地语义记忆 | 缺少目标平台固定的推理依赖约束，以及文本、图像向量模型的完整固定文件配方；现有手工模型下载脚本不能替代发布配方 |
| `follow` 人物跟随 | 依赖本地视觉感知和导航，继承感知模块的缺项 |
| `vision-memory`、`navigation-memory`、`full-*` | 包含上述未完成的模型模块 |
| Go2上的模型推理组合 | 还需与设备 JetPack（Jetson软件平台）版本一致的厂商推理依赖及实际导入、模型加载验证；通用 ARM64 构建成功不能证明厂商图形处理器依赖兼容 |
| `map2d`、`map2d-navigation` | 二维原生依赖及完整安装链需要独立发布验证，当前21包配置未包含它们 |

软件构建、离线网关检查和安装包校验覆盖软件交付过程。相机、雷达、惯性输入、外参、定位精度与运动行为仍需在实际设备上配置和验证。

## 首次安装管理入口

以设备普通用户操作。系统需具备对应版本的 Python；系统依赖安装和开机服务配置会单独请求管理员权限。

在有仓库访问权限的浏览器中打开[发布页](https://github.com/Molun0301/nuwax-embodied-harness/releases)，下载该版本的 `neh_bootstrap.py` 到设备。私有发布源的访问令牌应保存到仅当前用户可读的文件，例如 `~/.config/neh/github-token`，并设为 `0600` 权限。令牌需要能读取该仓库的发布附件。

```bash
chmod 600 "$HOME/.config/neh/github-token"
python3 neh_bootstrap.py --token-file "$HOME/.config/neh/github-token"
```

引导程序读取正式版本目录，核对管理包大小和 SHA256（安全散列算法）摘要，然后启动管理服务。终端会打印设备网络地址和命令行入口。默认管理页端口为 `8765`，业务网关端口为 `8766`；首次安装前可在管理设置中调整业务端口。

有桌面环境时会自动打开管理页。通过 SSH（安全远程连接）安装时，使用终端打印的设备网络地址，从同一网络的浏览器访问。需要仅在设备本机监听时，增加 `--host 127.0.0.1`。

纯命令行安装使用同一引导入口：

```bash
python3 neh_bootstrap.py --token-file "$HOME/.config/neh/github-token" --cli
```

默认安装目录为 `~/.local/share/neh`，命令行入口为 `~/.local/share/neh/bin/neh`。管理程序是独立进程，业务网关未启动时仍可查看安装任务、配置和版本。

## 安装业务模块

在管理页查看硬件识别结果，选择机器人、版本和模块，检查计划中列出的下载量、系统依赖及阻塞条件，然后执行。安装完成后配置设备连接并启动业务网关。首次设置和常用参数都可通过管理页或命令行保存。

命令行示例：

```bash
~/.local/share/neh/bin/neh hardware
~/.local/share/neh/bin/neh releases --refresh
~/.local/share/neh/bin/neh plan install --robot customrobot --modules core
```

计划返回 `id` 且没有阻塞条件后，使用该标识执行：

```bash
~/.local/share/neh/bin/neh apply 实际计划标识 --wait
~/.local/share/neh/bin/neh status
~/.local/share/neh/bin/neh start --wait
```

Go2可将机器人选择为 `go2`，例如模块选 `pointlio,navigation`。安装方案会使用该平台对应的业务包和官方依赖配方。传感器接线、机器人网络与标定需按实际设备设置。

预安装可以提供 JSON（结构化数据格式）文件：

```json
{
  "action": "install",
  "version": "0.1.0",
  "robot": "customrobot",
  "modules": ["core"],
  "configuration": {},
  "stop_running": false
}
```

```bash
python3 neh_bootstrap.py --token-file "$HOME/.config/neh/github-token" --configure 安装配置.json --no-browser
```

配置里的版本必须已存在于当前目录，平台和模块必须匹配。任务开始后关闭终端不会取消后台安装，可通过 `jobs` 和 `job 实际任务标识 --wait` 查看结果。

## 依赖、模型和下载缓存

业务包包含本项目源码、必要启动文件和已编译的自有程序。Python第三方轮子、原生第三方动态库及模型文件按清单分别获取，不嵌入业务归档。

- 普通 Python 依赖优先使用 PyPI（Python软件包索引）的官方文件。每个文件固定版本、大小和摘要，先下载并验证后安装。
- 需要随构建产生的独立原生依赖以单独附件提供，文件摘要纳入安装清单。
- Go2依赖使用登记的宇树官方源码、官方 CycloneDDS（数据分发中间件）预编译库及 Python 绑定来源。设备使用已核验的预编译库准备本机 Python 绑定，结果进入设备缓存；NEH发布包不携带自行重发的宇树或CycloneDDS轮子。
- 模型模块只有具备固定文件清单后才能发布。模型从独立来源下载，目录位于持久数据区，不因业务版本切换而重复进入业务包。
- 缓存复用前核对大小和摘要。下载中断可以重试；内容被修改或版本不同会重新获取，不能以文件名相同代替完整性检查。

首次安装下载量通常高于业务包大小。安装计划分别显示业务包、依赖和模型的下载量，更新时能复用已核验缓存。

## 更新、历史版本和恢复

管理页刷新版本后可选择目标版本。版本目录保留历史发布记录，切换版本时仍按当前设备平台和所选模块匹配。已经公开的版本和附件不会被同版本重新构建覆盖。

运行中的业务需要按计划停止后再更新；命令行显式使用 `--stop-running` 表示允许执行这一步。可先查看更新计划：

```bash
~/.local/share/neh/bin/neh releases --refresh
~/.local/share/neh/bin/neh plan update --version 实际目标版本 --stop-running
~/.local/share/neh/bin/neh apply 实际计划标识 --wait
```

管理程序自身通过 `update-manager --wait` 更新。业务版本恢复使用 `rollback --wait`；运行中的业务同时需要 `--stop-running`。任务记录会区分完成、失败、中断和恢复结果。持久配置、地图与已有记忆数据不属于业务归档，升级时继续使用。

## 维护者如何发布

发布配置为仓库根目录的 `.github/release.json`，包括版本、渠道、模块目标和发布说明。默认稳定渠道为 `stable`，预览渠道为 `preview`。

1. 递增配置中的版本，提交需要发布的代码与配方。
2. 合并到 `main` 时，发布配置的变化自动触发工作流；推送 `v主.次.修订` 格式的标签也会触发。
3. 也可在 Actions 页面运行“NEH正式构建与发布”。留空覆盖字段会使用完整配置；关闭发布选项时仅构建并保留附件供检查。
4. 工作流按真实平台运行三个构建组。同一平台共用基础依赖和原生编译缓存，但FastLIO2与PointLIO分别编译，最终业务包仍严格执行模块互斥约束。
5. 构建使用干净检出的提交，验证解释器、机器架构、依赖安装、原生动态链接及离线网关流程，再产生各模块包与成功回执。
6. 聚合任务核对21个目标是否全部存在、版本与源码提交是否一致、每个文件的大小和摘要是否匹配，并把新版本加入历史目录。
7. 发布任务先创建私有仓库中的版本草稿，上传全部附件并核对远端摘要，最后公开该仓库内的完整版本。任一目标、上传或核验失败都会停止最后的公开步骤。

重复运行同一已发布版本时，只有源码提交和目标集合一致才会直接结束。修订了源码、目标或配方后应递增版本；来自另一源码提交的旧草稿也不会被自动接管。

版本附件包括 `catalog.json`、`manager.tar.gz`、两个引导入口、业务归档、清单、依赖来源记录、发布计划和总文件索引。失败日志与检查结果保存在 Actions 构建附件中。容器和离线检查不代替真实机器人功能验收，发布结果中应分别记录两类证据。
