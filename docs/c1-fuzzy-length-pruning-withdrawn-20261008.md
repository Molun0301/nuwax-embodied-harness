# 文本匹配长度上界剪枝：已撤回

日期：2026-10-08。生产基线为 `62e950a71bf904ebb11dd83aa12d76336a0c80f1`。

## 决定

七行候选通过正确性检查，但没有通过预先设定的配对性能门槛，**不保留生产改动**。`services/memory/service.py` 已逐字恢复到基线；没有为了得到有利窗口重跑、增加样本或修改门槛。

候选只在现有 fuzzy-cache miss 且已有正分数时，使用与 `SequenceMatcher.ratio()` 相同运算顺序的长度上界；无法超过当前最佳结果的文本跳过完整匹配，不把上界当真实分数缓存。候选未增加缓存容量、锁、哈希或业务安全规则，但新增判断仍应有可靠收益才保留。

## 正确性证据

实际 CPython 3.8.20，目标 3.8.10 未执行。冻结基线与候选共 32,008 次分数位模式／理由差分通过，覆盖 564 组输入、四种缓存模式、冷列表、反向顺序、单项重访、暖列表、Unicode、空文本及 autojunk 边界。候选阶段 92 项单元检查及 recall 场景脚本通过。

发现原有差分测试先逐项评分、再测试整列表，会预热缓存而错过冷列表路径。保留的改动仅补齐这个覆盖缺口及相关边界：

- 缓存关闭、仅分数缓存、完整查询内缓存的冷列表先比较原公式，再运行单项和暖列表
- 明确覆盖 query 为 `a b`、文本依次为 `b a` 和 `a b`：即使前者 token overlap 达到1.0，后面的精确匹配仍按原语义返回0.99及精确理由
- 查询隔离、容量、异常清理、Unicode、199/200/201长度和非对称匹配仍覆盖

只针对候选剪枝次数的测试随候选从项目中撤回，其证据另行保留。恢复生产基线后的最终 service 回归 **37项通过**，零失败；不重算为候选提速证据。

## 一次预设测量

单次建立5,000条合成记录、固定seed3101、file-backed SQLite FULL及显式常量向量。总计22次完整查询：4次预热、8次A/A、8次A/B、2次独立调用计数；另有16次微型未计时控制。无cProfile/tracemalloc插桩，无模型、设备或原生构建。

A/A使用相同基线函数；A/B仅切换冻结的评分函数，不替换生产文件。顺序均为AB、BA、AB、BA。

预设门槛要求A/A的wall和CPU配对中位偏差不超过5%，各标签相对MAD不超过10%。A/B还须wall及CPU中位收益达到至少5%（或两倍A/A偏差，取大者）、至少3/4配对更快、相对MAD不超过10%、真实匹配调用数减少、输出投影及缓存/持久化聚合一致。
