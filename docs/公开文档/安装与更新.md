# 安装与更新

NEH（具身运行框架）通过独立管理程序安装、更新和管理业务版本。普通用户从公开仓库匿名安装；管理网页和 `neh` 命令共用同一任务流程。

## 一条命令安装并打开网页

在目标 Linux（操作系统）设备的普通用户终端执行，终端需有 curl（下载工具）：

```bash
curl -fsSL https://raw.githubusercontent.com/Molun0301/nuwax-embodied-harness/main/get-neh.sh | bash
```

安装入口按需准备 Python（编程语言）和 Git（版本控制工具），安装管理程序与服务。有桌面环境时自动打开管理网页；远程终端会打印网址，在浏览器打开该地址。缺少系统工具或安装系统服务时，终端会单独请求管理员密码。

管理端口默认从 8765 开始选择，复用本安装已保存的端口；端口占用时自动选空闲值，并避开默认 8766 的业务网关端口。**以安装输出的实际网址为准。**管理页用于软件安装与维护，业务控制台用于地图、任务和设备操作。

管理页打开后，选择安装目录、机器人和模块，查看计划并安装。基础网关可独立安装；二维建图、FastLIO2（快速激光惯性里程计）、PointLIO（逐点激光惯性里程计）可共同安装，需要导航时再选择导航模块。实际使用的建图链路和定位后端由机器人配置决定。系统和传感器准备见[安装前准备](安装前准备.md)，第一次接入设备见[快速上手](快速上手.md)。

安装器把命令入口链接到 `~/.local/bin/neh`。若该目录不在 PATH（命令搜索路径）中，按安装输出提示设置后重新打开终端；也可使用输出中的 `bin/neh` 完整路径。已有旧安装或自定义管理目录时继续使用原入口。

```bash
neh
neh update
```

`neh` 默认显示当前状态。`neh update` 完成检查、必要的管理程序自更新、候选准备、空闲检查、切换重启与健康核验；失败时尝试恢复上一有效版本。关闭终端或网页不会取消已经受理的任务。

## 日常更新与恢复

管理网页顶部显示可用更新和“立即更新”入口，命令行可使用：

| 命令 | 用途 |
| --- | --- |
| `neh` 或 `neh status` | 查看当前版本、模块、运行状态与更新提醒 |
| `neh update --check` | 只检查更新 |
| `neh update` | 准备并安装新版本，等待任务结果 |
| `neh update --local-build` | 五个可预编译程序的云端编译尚未完成时，选择立即在本机编译；LIO 始终本机编译 |
| `neh update --retry` | 处理原因后，明确重试此前失败的修订 |
| `neh jobs` / `neh job 任务标识 --wait` | 查询任务或继续等待 |
| `neh start --wait` / `neh stop --wait` | 按已有拥有方启停业务并核对结果 |
| `neh rollback --stop-running --wait` | 切回本机保留的上一有效业务版本 |

默认通道为 `main`（主分支）。分支更新只接受远端沿当前版本继续向前的提交；当前版本领先或历史分叉时显示实际状态，不提示安装旧版本。需要改变来源时主动选择目标通道，确认版本与设备兼容性：

```bash
neh channel main
neh channel branch:分支名称
```

目前没有承诺稳定版标签通道。历史 `v0.1.0` 发布继续保留供旧安装迁移，日常安装不需要下载该版本附件。

相同提交、模块和配置没有变化时，不重新构建或重启。下载、构建或候选检查失败时保留旧版本；切换或启动检查失败时尝试回退，页面和任务记录会显示结果。失败修订会被记住，后台不会反复尝试；修复原因后用 `--retry` 明确重试。回退业务程序不会自动逆转数据格式迁移，升级前应保存重要配置、地图及记忆数据库。

`neh plan update --stop-running` 和 `neh apply 计划标识 --wait` 保留供需要逐项审查的流程使用。普通更新直接运行 `neh update`。查看配置、模块、详细日志和回退结果仍可使用同一管理网页。

## 检查提醒与空闲安装

默认使用 `notify`（仅提醒）：约每 30 分钟检查一次，并加入随机抖动，发现更新后提醒，等待用户点击安装。需要改变策略或指定维护时间窗时：

```bash
neh auto-update off
neh auto-update notify
neh auto-update idle --window 02:00-05:00
```

| 档位 | 行为 |
| --- | --- |
| `off`（关闭） | 关闭后台定时检查；可手动检查和更新 |
| `notify`（仅提醒，默认） | 定时检查与提醒，等待用户执行更新 |
| `idle`（空闲时安装） | 可先准备候选版本，在设备空闲且进入维护时间窗后安装 |

时间窗采用设备本地时间，格式为 `HH:MM-HH:MM`。标记为需人工确认的版本只提醒，由用户执行更新。

手动更新和后台安装共用设备空闲门禁：没有活动任务，并通过网关的 readiness（安全就绪状态）确认。存在执行器时，需要新鲜状态确认电机未使能；设备明确声明没有执行器时使用相应契约。状态缺失、过期、断连、任务仍在运行或电机使能时，继续等待并显示原因。候选准备会降低调度优先级，实际切换仍需重新检查状态和时间窗；无法确认安全停机时不执行切换。

## 云端预编译与本机缓存

云端只为以下五个程序提供预编译加速：

| 程序 | 用途 |
| --- | --- |
| `nuwax-slam-2d-worker` | 二维建图工作进程（slam2d worker） |
| `nuwax-geometry-runtime` | 几何运行时（geometry runtime） |
| `nuwax-nav-stack` | 导航程序（nav stack） |
| `nuwax-person-follow` | 人物跟随程序（person-follow） |
| `nuwax-mapping-cli` | 建图命令工具（mapping-cli） |

这五个程序的预编译目标平台为：

| 平台标识 | 目标环境 |
| --- | --- |
| `focal-arm64` | Ubuntu 20.04、64 位 ARM（精简指令集架构），面向 Go2 |
| `noble-x86_64` | Ubuntu 24.04、64 位 x86 |

这五个程序按源码、锁文件、工具链和构建参数计算输入指纹，复用相同指纹的已验证产物；变化的程序才重新下载或构建。下载的程序先核对摘要和平台，候选版本准备成功后才允许切换。附件缺失、校验错误或不匹配时回到本机编译；其它系统和架构使用本机编译路径。

FastLIO2 与 PointLIO 始终由设备获取固定源码，在本机使用稳定源码和构建缓存增量编译。它们不进入云端预编译或索引，也不在 Release（发布集合）提供二进制或额外 LIO 源码包。两个程序包含 Dimensional Inc. 的 Apache-2.0 包装与 `dimensionalOS/dimos-module-fastlio2` 的 GPL-2.0 算法；设备或镜像出货预装其编译产物前需兼容授权，见[第三方许可证说明](第三方许可证说明.md#lio-程序的源码编译与分发范围)。

开发分支的上述五个可预编译程序没有对应源码提交的云端索引时，默认每 900 秒重新检查并显示“云端编译中”。希望立即编译可用 `neh update --local-build`。LIO 直接使用本机源码缓存增量编译，不等待云端索引。Python 依赖与模型继续按设备配方下载、缓存和准备，未放入原生预编译附件。

### 推送通过后多久能看到更新

默认定时检查间隔约为 27—33 分钟。设备持续在线、网络正常，且通道文件已经在该设备的下载链路可见后，下一轮检查最长约 33 分钟；正在等待云端索引的任务则每 15 分钟重查。构建耗时、设备离线时间和外部缓存传播时间需要另外计算，不能承诺从推送通过起固定多少分钟内必定提醒。

隔离故障验收的真实下载记录中，同名附件覆盖后曾连续 65 秒读到旧内容并命中缓存；另一路径在上传约 3 分 15 秒后已读到新内容。这是具体路径的观察，不是所有地区缓存延迟的上限。程序附件按指纹使用不可变 URL（下载地址），不原地替换内容；开发提交的索引即使先被请求而返回 HTTP 404（暂不可见），设备仍稍后重查。

main 通道暂时返回 404、通道提交不比本机新，或固定索引仍是旧提交、缺少所选程序时，设备保留当前安装，正常提示稍后再查，不降级、不反复启动本机编译。管理程序把已校验的完整索引交给同一更新任务使用，避免构建子进程再次请求时命中旧 404。真正的程序附件缺失或摘要不符，仍按该程序回退本机增量编译；严格摘要校验保持开启。

本机源码、构建目录和依赖缓存会保留，后续更新可以增量构建。当前运行版本使用独立源码与程序，不直接运行可变构建缓存。缓存尚无统一容量上限，长期维护时应按实际占用检查；当前与回退版本、配置、地图和模型不应当作临时缓存删除。

维护者推送后由 CI（持续集成）运行源码检查和上述五个程序的预编译。发布附件位于公开的 `neh-prebuilt-v1` Release：`index-完整提交.json` 对应固定提交且只列上述五个程序；`channels-main.json` 对应设备的 `main` 通道，逻辑上是 `channels/main.json`。主分支测试和五程序预编译全部完成后才更新通道附件，开发分支只生成自己的索引。设备按固定索引、摘要及实际文件核验产物。许可证及对应源码交付要求见[第三方许可证说明](第三方许可证说明.md)。

本轮产品化改动先在功能分支验收，经用户确认后合入 fix 分支；阶段0入口分支不单独合入 main。main 通道的实际发布验证延后到未来 fix 整体合入 main 后进行。

预编译完成表示软件产物完成准备。本次阶段 0—3 没有完成阶段 4 的 Go2 实机迁入及运动、建图、导航验收；实际设备仍需独立现场验证。

## 自定义安装位置

新安装默认位于 `~/Nuwax-embodied-harness`。网页“硬件检查”可输入或浏览目标设备上的父目录，保存前显示最终位置，例如选择 `/mnt/data` 后使用 `/mnt/data/Nuwax-embodied-harness`。父目录可以已有其它文件；最终文件夹存在无关内容或属于其它安装时会报告冲突，实际目录须由当前用户持有且其它用户不可写。

网页选择的业务目录承载业务版本、源码与构建缓存、配置、模型和数据。管理程序与任务记录保留在最初管理目录，网址及 `neh` 入口继续可用。已有成功安装的业务位置只读，迁移需重新安装并显式迁移配置和数据；更改页面路径不负责搬迁文件。

若连管理程序也需要放在自定义位置，给安装入口传完整目标路径：

```bash
curl -fsSL https://raw.githubusercontent.com/Molun0301/nuwax-embodied-harness/main/get-neh.sh | bash -s -- --install-dir "$HOME/NEH 数据"
```

`--home` 与 `--install-dir` 同义，`NEH_HOME` 也可指定管理根目录，显式参数优先。它们表示完整路径，不追加文件夹名称。重跑引导时使用原管理目录，另选目录会创建独立管理入口。已有 `~/.local/share/neh` 安装仍沿用原位置。

终端交互安装用 `bash -s -- --cli`。默认安装只准备管理程序，网页选择模块后才安装业务；无人值守业务安装也可提交 JSON（结构化数据格式）配置：

```json
{
  "action": "install",
  "robot": "customrobot",
  "modules": ["core"],
  "configuration": {},
  "stop_running": false
}
```

```bash
neh apply --file 安装配置.json --wait
```

Go2 使用 `"robot": "go2"`，厂商依赖按固定官方配方准备；传感器、网络和真实标定仍按设备配置。

## 旧管理程序迁入

旧管理程序若仍调用已经退役的 `product_release` 源码组装入口，首次迁到当前版本时，用当前引导脚本对**原管理根目录**重跑一次安装，显式传原 `--install-dir`，沿用原仓库、分支和服务方式；管理任务结束后再操作。

引导器读取既有安装记录，准备并切换管理版本，保留原业务安装与数据；切换失败按原事务恢复入口与配置。使用旧安装目录里的旧引导器不能完成这次迁移。迁入后日常更新使用 `neh update`；已有 `update-manager --wait` 入口继续保留供单独维护管理程序。

## 卸载与数据保留

```bash
neh uninstall
```

卸载先确认当前实例没有安装任务、业务能够安全停止，再停止属于该实例的业务及管理服务，移除程序和本实例创建的命令链接。默认保留配置、地图、模型、缓存和其它业务数据，结果会显示实际目录。其它安装的进程或服务不会被认领。

确认需要同时删除当前实例管理目录和业务目录中的全部内容时：

```bash
neh uninstall --purge
```

`--purge`（清空数据）会删除配置、地图、模型及业务数据。执行前应核对目录与备份。设备系统共享依赖按操作系统的软件包管理方式处理。

源码开发安装、已有 Go2 开发机推送和源码更新恢复见[开发工具使用指南](开发工具使用指南.md#源码开发安装)。
